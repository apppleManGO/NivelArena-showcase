# 온라인의 나머지 절반 — 무엇을 보내지 *않을* 것인가

> Unity TCG(니벨아레나) 개발기 3편.
> [1편](01-단일관문-GameActionGateway.md)에서 "호스트가 실행하고 **결과 상태를 복제한다**"고 적고 넘어갔습니다.
> 그 복제가 실제로 어떻게 생겼는지, 그리고 카드 게임에서 가장 중요한 **숨겨진 정보**를 어떻게 다뤘는지에 대한 글입니다.

---

## 1. 갈림길 — 네트워크로 무엇을 보낼 것인가

멀티플레이 동기화에는 크게 두 갈래가 있습니다.

**A. 행동만 보내고 양쪽이 각자 계산한다** (결정론적 lockstep — RTS가 주로 씁니다)

```
클라: "레인2에 이 카드 배치했음"  →  양쪽이 똑같이 계산  →  같은 결과
```

대역폭이 거의 들지 않습니다. 유닛이 수백 개인 RTS도 명령만 주고받으면 되니까요.

**B. 호스트가 계산하고 결과 상태를 통째로 보낸다** (상태 복제)

```
호스트: 계산  →  "지금 판이 이렇게 생겼다" 사진 한 장 전송  →  클라는 따라 그림
```

이 프로젝트는 **B**를 골랐습니다. A의 전제가 무섭기 때문입니다.

> A는 **양쪽의 계산이 영원히 한 치도 어긋나지 않아야** 합니다.

이 게임에는 카드 효과가 700종 있고, 그 안에 셔플·랜덤 선택·순서 의존 처리가 잔뜩 들어 있습니다.
`Dictionary` 순회 순서 하나만 달라도 결과가 갈립니다.

그리고 A의 진짜 문제는 **한 번 어긋나면 영원히 어긋난다**는 것입니다.
두 화면이 서서히 다른 게임이 되는데 아무도 눈치채지 못합니다. 디버깅이 지옥이 됩니다.

B는 매번 정답을 통째로 다시 보내므로, **어긋나도 다음 스냅샷이 자동으로 교정**합니다.
카드 게임은 초당 60번 동기화할 필요도 없으니 이 사치를 부릴 수 있습니다.

> 🎬 A는 **양쪽이 같은 레시피로 요리하기**, B는 **한쪽이 요리해서 사진을 보내기**입니다.
> 실시간성이 생명이면 A, **정확성이 생명이면 B**.

## 2. 스냅샷 해부 — 판 전체가 배열 하나

`BroadcastState()`가 만드는 페이로드입니다.

```csharp
object[] payload = {
    f,                     // 0  : 필드 6칸 (카드ID 문자열)
    tm.IsPlayerTurn,       // 1  : 지금 누구 턴인가
    (byte)tm.CurrentPhase, // 2  : 페이즈
    clientHand,            // 3  : 클라의 손패 — 카드ID 전부
    oppHandCount,          // 4  : 호스트의 손패 — 개수만!
    // 호스트 자신의 존 (5~9)
    pP.LeaderLevel, pP.IsAwakened, pDmg, pP.DrawPile.Count, pTrash,
    // 상대(클라)의 존 (10~14)
    pO.LeaderLevel, pO.IsAwakened, oDmg, pO.DrawPile.Count, oTrash,
    items,                 // 15 : 레인별 장착 아이템
};
```

**게임 한 판의 상태 전체가 16칸짜리 배열**입니다.

그리고 카드는 전부 `CardId` 문자열로만 오갑니다. 양쪽이 같은 카드 에셋을 빌드에 갖고 있으므로,
`"BT07-045"` 다섯 글자면 카드 한 장이 통째로 복원됩니다. 스탯도 효과도 보낼 필요가 없습니다.

덤으로 이게 **치트 방지**이기도 합니다. 클라가 "내 카드 파워는 99999"라고 우겨도,
호스트는 자기 에셋을 보고 계산하니까요.

## 3. ★ 이 설계의 핵심 — 무엇을 *안* 보낼 것인가

이 페이로드에서 가장 잘 설계된 부분은 **보내는 것**이 아니라 **보내지 않는 것**입니다.
카드 게임은 숨겨진 정보가 곧 게임성이니까요.

```csharp
// 손패: 클라의 손패는 카드ID로 → 클라가 자기 손패를 복원
//       호스트 자신 손패는 "개수만" → 클라엔 상대 뒷면 개수 (내용 숨김 = 히든 정보 보호)
var clientHand   = pO.Hand.Select(c => c.CardId).ToArray();   // 내용 전부
int oppHandCount = pP.Hand.Count;                              // 숫자 하나

// 존: 대미지존·트래시는 앞면 공개라 내용(카드ID)까지, 덱은 순서 숨김이라 개수만
var pTrash = pP.TrashPile.Select(c => c.CardId).ToArray();      // 내용 전부
pP.DrawPile.Count                                               // 숫자 하나
```

전송 범위가 **게임 규칙 그대로** 매핑돼 있습니다.

| 존 | 실제 게임에서 | 보내는 것 |
|---|---|---|
| 필드 | 서로 다 보임 | 카드 ID 전부 |
| 트래시 | 앞면, 누구나 열람 가능 | 카드 ID 전부 |
| 대미지존 | 앞면 공개 | 카드 ID 전부 |
| **내 손패** | 나만 봄 | 나에게만 카드 ID |
| **상대 손패** | 장수만 보임 | **개수만** |
| **덱** | 아무도 못 봄 | **개수만** |

여기서 이 글에서 가장 중요한 문장이 나옵니다.

> **안 보낸 정보는 치트로도 볼 수 없습니다.**
>
> 화면에서 가리기만 했다면 메모리를 뜯거나 UI 코드를 조작해서 다 볼 수 있습니다. 흔한 온라인 게임 핵이 이런 식입니다.
> 하지만 **애초에 전송하지 않으면** 클라이언트 컴퓨터 어디에도 그 정보가 없습니다. 뜯을 것이 없습니다.

덱을 개수만 보내는 것도 같은 이유입니다. 순서가 새면 다음에 뽑을 카드를 전부 알게 되니까요.

### 그럼 개수만 받은 걸 어떻게 그리나

재밌는 절충이 하나 있습니다.

```csharp
// 상대 손패 개수 표시용 플레이스홀더 (내용 안 보이는 뒷면이라 빈 카드로 충분)
private static CardData HandPlaceholder()
    => _handPlaceholder ??= ScriptableObject.CreateInstance<CardData>();

// 받는 쪽
oppPc.Hand.Clear();
for (int i = 0; i < oppCount; i++) oppPc.Hand.Add(HandPlaceholder());
```

**내용이 텅 빈 카드 하나를 만들어 N개 집어넣습니다.** 어차피 뒷면으로 그려지니 내용이 필요 없습니다.
덱도 마찬가지입니다.

```csharp
DrawPile.Clear(); for (int i = 0; i < drawCount; i++) DrawPile.Add(placeholder);
```

`Hand.Count`를 세서 카드를 그리는 기존 UI 코드를 **한 줄도 고치지 않고** "개수만 아는 상태"를 표현했습니다.

## 4. ★ 미러 관점 — 호스트의 "상대"가 클라에겐 "나"다

두 번째 핵심입니다. 이 게임의 모든 코드는 `bool isPlayer`로 편을 구분합니다. `true`=나, `false`=상대.
그런데 **온라인에서는 이게 사람마다 반대**입니다.

```
호스트 화면:  아래쪽(true) = 호스트 자신     위쪽(false) = 클라
클라 화면:    아래쪽(true) = 클라 자신       위쪽(false) = 호스트
```

호스트가 보낸 스냅샷은 호스트 관점이므로, 클라는 받아서 **뒤집어야** 합니다.

```csharp
// 필드 미러: 호스트 플레이어(f[0..2]) → 클라의 상대(false)
//            호스트 상대(f[3..5])     → 클라의 나(true)
for (int i = 0; i < 3; i++) fm.ReplicateSetUnit(false, i, CardLookup.ById(f[i]));
for (int i = 0; i < 3; i++) fm.ReplicateSetUnit(true,  i, CardLookup.ById(f[3 + i]));
```

존도 교차합니다.

```csharp
var myPc  = PlayerController.PlayerInstance;  // 클라 자신
var oppPc = PlayerController.AIInstance;      // 상대(호스트)

myPc.ReplicateZones( payload[10], payload[11], ... );  // 호스트가 보낸 "상대 존"(10~14) → 내 존
oppPc.ReplicateZones(payload[5],  payload[6],  ... );  // 호스트가 보낸 "자기 존"(5~9)   → 상대 존
```

턴 표시까지 뒤집힙니다.

```csharp
// 턴 미러: 호스트의 턴(true) = 클라 입장에선 상대 턴(false)
TurnManager.Instance?.ApplyNetworkTurn(!hostIsPlayerTurn, phase);
```

`!` 하나가 "지금 내 턴인가"를 결정합니다.

> 여기서 배울 점은 **관점 변환이 딱 한 함수 안에만 있다**는 것입니다.
> `OnStateReceived()`를 통과하고 나면 그 뒤의 모든 코드(`FieldManager`, `HUDView`, `LaneSlot`…)는 평소처럼 "true=나"로 동작합니다.
> 뒤집기가 여기저기 흩어졌다면 어딘가에서 하나 빠뜨려 **상대 카드가 내 자리에 그려지는** 버그가 났을 겁니다.
> 1편의 "경계를 한 곳에 가둔다"가 여기서도 그대로 반복됩니다.

## 5. 복제 전용 통로 — 클라는 실행하지 않는다

가장 오해하기 쉬운 지점을 짚고 갑니다.

> ❌ 호스트: "배치해도 돼" → 클라가 배치를 실행
> ✅ 호스트가 직접 실행 → 결과 스냅샷 전송 → 클라는 그리기만

클라에는 **게임 로직을 실행할 통로 자체가 없습니다.** 복제 전용 함수만 있습니다.

```csharp
// 3c 상태 복제 전용: 필드를 직접 세팅(효과·트래시·검증 없이 UI 이벤트만 발생)
public void ReplicateSetUnit(bool isPlayer, int lane, CardData card)
{
    _field[owner, lane] = card;                              // 값만 대입
    if (card == null) OnUnitRemoved?.Invoke(isPlayer, lane);  // 화면 갱신 이벤트만
    else              OnUnitPlaced?.Invoke(isPlayer, lane, card);
}
```

만약 클라가 평범한 `PlaceUnit()`을 호출했다면?

```
PlaceUnit() → 검증 → 배치 → EffectSystem.OnUnitPlaced() → 엔트리 효과 발동!
                                                            ↑ 여기가 문제
```

**엔트리 효과가 클라에서 또 터집니다.** 호스트에서 이미 드로우를 처리했는데 클라에서 또 드로우하는 셈입니다.

> 1편의 **"클라는 화면이다"** 가 코드로 표현된 지점이 여기입니다.
> 2편의 **"클라는 턴 루프 코루틴을 시작조차 하지 않는다"** 도 같은 이야기의 다른 층위였습니다.

## 6. 언제 보내는가 — 다섯 지점

`BroadcastState()` 호출 지점을 전부 찾아보면 이렇습니다.

```
GameActionGateway  — 행동 실행 성공 직후
TurnManager        — 페이즈가 바뀔 때마다
CombatManager ×2   — 공격 코루틴이 끝난 뒤 (2편에서 다룬 그 이유)
GameManager  ×2    — 멀리건 전/후
```

전략은 단순합니다. **"상태가 바뀌었을 만한 모든 지점에서 전부 다시 보낸다."**

델타(바뀐 것만)를 계산해 보내면 효율적이겠지만, 그러려면 "무엇이 바뀌었는지" 추적하는 코드가 필요하고
그게 또 버그의 온상이 됩니다. **전체를 매번 보내는 건 무식하지만 틀릴 수가 없습니다.**

## 7. 전송 수단 — RPC가 아니라 `RaiseEvent`

Photon(PUN)에는 원격 호출 방식이 두 가지 있습니다.

```csharp
// ① PunRPC — 저쪽의 "함수 이름"을 불러 실행시킨다
photonView.RPC("PlaceUnit", RpcTarget.Others, lane, cardId);

// ② RaiseEvent — 번호 붙인 "우편"을 보낸다
PhotonNetwork.RaiseEvent(EV_STATE, payload, options, sendOptions);
```

이 프로젝트는 **`PunRPC` 0회, `RaiseEvent` 30회**로 ②만 씁니다.

이유는 5장과 같습니다. ①은 "저쪽 함수를 실행시킨다"는 발상이라 **클라가 게임 로직을 실행하게 되기 쉽습니다.**
②는 데이터를 보낼 뿐이고, 받는 쪽이 그걸 어떻게 해석할지 스스로 정합니다.
그 해석 지점이 5장의 `Replicate*` 함수들이고요.

우편 종류는 12개입니다.

```csharp
private const byte EV_ACTION       = 1;  // 클라→호스트 행동 전송
private const byte EV_DEFENSE_REQ  = 2;  // 호스트→클라 방어 요청
private const byte EV_DEFENSE_RESP = 3;  // 클라→호스트 방어 응답
private const byte EV_STATE        = 4;  // 호스트→클라 상태 복제
private const byte EV_ENDPHASE     = 5;  // 클라→호스트 페이즈 종료
private const byte EV_CARD_REQ     = 6;  // 호스트→클라 카드 선택 요청
private const byte EV_CARD_RESP    = 7;  // 클라→호스트 카드 선택 응답
private const byte EV_MULL_REQ     = 8;  // 호스트→클라 멀리건 요청
private const byte EV_MULL_RESP    = 9;  // 클라→호스트 멀리건 응답
private const byte EV_GAMEOVER     = 10; // 호스트→클라 승패 결과
private const byte EV_TOAST        = 11; // 호스트→클라 커멘터리
private const byte EV_TRIGGER      = 12; // 호스트→클라 트리거 공개
```

**주석의 화살표 방향을 보면 권한 구조가 그대로 보입니다.**
클라→호스트는 전부 "요청/응답"이고, 호스트→클라는 "결과" 아니면 "요청"입니다.
클라가 호스트에게 무언가를 실행시키는 우편은 하나도 없습니다.

받는 쪽은 스위치 하나로 분배합니다.

```csharp
public void OnEvent(EventData photonEvent)
{
    switch (photonEvent.Code)
    {
        case EV_ACTION: OnActionReceived(photonEvent); break;
        case EV_STATE:  OnStateReceived(photonEvent);  break;
        // ...
    }
}
```

### 그리고 "서버"가 아니라 "호스트"입니다

```
[전용 서버 방식]              [이 프로젝트 = 호스트 권위]
  클라A ─┐                      클라A(호스트) ←→ 클라B
         ├→ 게임 서버                    ↑
  클라B ─┘  (게임 로직 실행)       이 사람 컴퓨터가 심판
```

Photon Cloud는 게임 로직을 전혀 모릅니다. A가 보낸 데이터를 B에게 전달하는 **릴레이**일 뿐입니다.
심판은 플레이어 중 한 명, 방을 만든 사람의 컴퓨터입니다.

```csharp
public bool IsAuthority => PhotonNetwork.IsMasterClient;   // 방장이 곧 심판
```

서버 비용이 0이라 "친구용"에는 딱 맞지만, **호스트 본인이 자기 클라이언트를 조작하는 것은 막을 수 없습니다.**
상용 게임이 전용 서버를 쓰는 이유가 이것입니다.

## 8. 이 방식의 대가

### ① 연출이 사라진다

스냅샷은 **결과**만 담습니다. "카드가 날아가 부딪혀 파괴됐다"가 아니라 "지금 그 레인은 비어 있다"만 전달됩니다.
그래서 클라 화면에서는 **카드가 순간이동**합니다.

이걸 메우려고 별도 이벤트를 얹어야 했습니다.

```
EV_TOAST    — "상대: OO 배치" 커멘터리 토스트 릴레이
EV_TRIGGER  — 트리거로 뒤집힌 카드를 클라에도 보여주기
```

> **상태 복제는 "무슨 일이 있었는지"를 알려주지 않습니다.** 이건 구조적 한계이고, 이벤트 릴레이는 그 위에 얹은 보완재입니다.

### ② 대역폭을 쓴다

매번 필드 6칸 + 손패 전체 + 트래시 전체를 보냅니다. 트래시가 20장이면 그것도 매번 전송됩니다.
TCG니까 괜찮지만, 액션 게임이었다면 불가능한 방식입니다.

### ③ 순서가 보장돼야 한다

```csharp
SendOptions.SendReliable
```

스냅샷이 순서 없이 도착하면 **옛 상태가 최신 상태를 덮어씁니다.** 판이 과거로 되돌아갑니다.
신뢰성 전송이 필수입니다.

## 9. 정리

- 동기화 방식은 **행동 재생(A)** 과 **상태 복제(B)** 중 B. 효과 700종의 계산이 양쪽에서 완벽히 일치할 거라 믿을 수 없었고, **B는 어긋나도 다음 스냅샷이 교정**하기 때문.
- 스냅샷은 **16칸 배열 하나**. 카드는 전부 `CardId` 문자열로 오간다(공유 에셋 덕분에 가볍고, 덤으로 치트 방지).
- **보내지 않는 것이 곧 보안이다.** 상대 손패와 덱은 개수만 보내, 클라 메모리에 애초에 존재하지 않게 했다.
- **관점 변환(`true`↔`false`)은 `OnStateReceived` 한 함수에만 가둔다.** 통과 후엔 모든 코드가 평소대로 동작한다.
- 복제는 **전용 통로**로만 들어온다 — 값 대입 + UI 갱신뿐, 게임 로직은 없다. 클라는 실행하지 않는다.
- 대가는 **연출 손실**. 스냅샷은 결과만 담으므로 토스트·트리거 공개는 별도 이벤트로 릴레이해야 했다.

1편과 나란히 놓으면 시리즈의 축이 완성됩니다.

> **1편: 행동은 한 방향으로 올라간다** (클라 → 호스트)
> **3편: 상태는 한 방향으로 내려온다** (호스트 → 클라)
>
> 이 두 방향이 만나 **"권위는 하나, 나머지는 화면"** 이라는 하나의 원칙이 된다.
