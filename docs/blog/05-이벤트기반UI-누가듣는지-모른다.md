# 로직이 UI를 모르게 하는 법 — 그리고 우리 코드가 그걸 못 지킨 이유

> Unity TCG(니벨아레나) 개발기 5편.
> 앞선 글들이 "이렇게 설계했다"였다면, 이번엔 **"여기까지만 지켰다"** 는 이야기입니다.
> 원칙이 무너진 지점과 그 이유를 그대로 적었습니다.

---

## 1. 문제 — 로직이 UI를 알기 시작하면

카드를 한 장 배치하면 화면에서 여러 곳이 바뀝니다.

```
레인에 카드 그림이 뜨고 · 손패가 재정렬되고 · 코스트 숫자가 줄고 · 사이즈 표시가 바뀌고…
```

가장 단순한 구현은 배치 처리 안에서 UI를 직접 부르는 것입니다.

```csharp
// 😱 FieldManager 안에서
public void PlaceUnit(bool isPlayer, int lane, CardData card)
{
    _field[owner, lane] = card;
    LaneSlot.Refresh(lane);            // UI 직접 호출
    HandView.Instance.RefreshHand();
    HUDView.Instance.RefreshStatus();
}
```

동작은 합니다. 문제는 **`FieldManager`가 화면 구성을 전부 알아야 한다**는 것입니다.

- UI를 하나 추가할 때마다 `FieldManager`를 열어 호출을 추가해야 하고
- UI를 지우면 여기도 지워야 하고
- **UI가 없는 상태(테스트, 서버)에서는 아예 돌지 않습니다**

---

## 2. 해법 — "일이 생겼다"고 방송만 한다

```csharp
// FieldManager
public event Action<bool, int, CardData> OnUnitPlaced;   // isPlayer, lane, card
public event Action<bool, int>           OnUnitRemoved;  // isPlayer, lane

public void PlaceUnit(bool isPlayer, int lane, CardData card)
{
    _field[owner, lane] = card;
    OnUnitPlaced?.Invoke(isPlayer, lane, card);   // "레인2에 카드가 놓였습니다"
}
```

`FieldManager`는 **누가 듣는지 모릅니다.** 아무도 안 들으면 `?.`가 조용히 넘어갑니다.

듣는 쪽이 스스로 손을 듭니다.

```csharp
// LaneSlot
private void Start()
{
    FieldManager.Instance.OnUnitPlaced          += OnUnitPlaced;
    FieldManager.Instance.OnUnitRemoved         += OnUnitRemoved;
    CombatManager.Instance.OnAttackStateChanged += RefreshAttackState;
    TurnManager.Instance.OnPhaseChanged         += OnPhaseChanged;
    RefreshUI();
}
```

> 📻 **라디오 방송국**과 같습니다. 방송국은 청취자가 몇 명인지 모릅니다. 그냥 송출하고, 듣고 싶은 사람이 주파수를 맞춥니다.

### 걸러 듣는 건 듣는 쪽 책임

방송은 레인 슬롯 6개 전부에게 갑니다. 그래서 각자 확인합니다.

```csharp
private void OnUnitPlaced(bool isPlayer, int lane, CardData card)
{
    if (isPlayer == IsPlayerLane && lane == LaneIndex)   // "내 얘기인가?"
    {
        _occupiedCard = card;
        RefreshUI();
    }
}
```

`FieldManager`가 "2번 레인 슬롯을 찾아서" 부르는 게 아니라, **6개가 다 듣고 자기 것만 반응**합니다.
덕분에 `FieldManager`는 슬롯이라는 것이 존재하는지조차 몰라도 됩니다.

## 3. `+=` 를 썼으면 반드시 `-=`

이벤트를 쓸 때 가장 흔히 빼먹는 부분입니다.

```csharp
private void OnDestroy()
{
    if (FieldManager.Instance  != null) FieldManager.Instance.OnUnitPlaced  -= OnUnitPlaced;
    if (CombatManager.Instance != null) CombatManager.Instance.OnAttackStateChanged -= RefreshAttackState;
    if (TurnManager.Instance   != null) TurnManager.Instance.OnPhaseChanged -= OnPhaseChanged;
}
```

해제하지 않으면 이렇게 됩니다.

```
씬 전환 → LaneSlot 파괴
       → 그런데 FieldManager의 이벤트 목록엔 아직 등록돼 있음
       → 다음 방송 때 파괴된 오브젝트의 메서드가 호출됨
       → MissingReferenceException, 또는 죽은 오브젝트가 메모리에 붙잡힘
```

**이벤트는 참조를 붙잡습니다.** 구독자가 죽어도 발행자가 손을 놓지 않으면 GC가 수거하지 못합니다.
C# 이벤트의 대표적인 메모리 누수 패턴입니다.

`if (Instance != null)` 체크가 붙은 것도 이유가 있습니다. **종료 순서를 보장할 수 없기 때문**입니다.
`FieldManager`가 먼저 파괴됐다면 `Instance`는 이미 `null`입니다.

---

## 4. 그런데 실제 코드를 세어보면

여기서부터가 솔직한 이야기입니다.

| 방식 | 개수 | 예시 |
|---|---|---|
| **이벤트 구독** (방송형) | **8곳** | `OnUnitPlaced`, `OnPhaseChanged`, `OnAttackStateChanged` |
| **직접 호출** (푸시형) | **150곳 이상** | `RefreshHand()` 87회, `NotifyStatusChanged()` 49회, `NotifyDamageChanged()` 11회 |

**압도적으로 직접 호출이 많습니다.** 카드 효과 코드가 이렇게 생겼습니다.

```csharp
private void H_EntryDraw(bool isPlayer, int lane, CardData card, int value, string et)
{
    GetOwner(isPlayer).DrawCard(value);
    HandView.Instance?.RefreshHand();      // ← UI를 직접 부른다
    HUDView.NotifyStatusChanged();         // ← 여기도
}
```

원칙대로면 `DrawCard()`가 이벤트를 쏘고 `HandView`가 구독하면 됩니다.
그러면 **효과 핸들러 440개에서 저 두 줄이 사라집니다.**

## 5. 왜 이렇게 됐나 — 원인은 캡슐화였다

`PlayerController`를 열어보면 답이 나옵니다.

```csharp
public List<CardData> Hand       { get; private set; } = new();
public List<CardData> DrawPile   { get; private set; } = new();
public List<CardData> TrashPile  { get; private set; } = new();
public List<CardData> DamageZone { get; private set; } = new();
```

`private set`이라 리스트를 **통째로 교체하는 것**은 막혀 있습니다. 그런데 **내용을 휘젓는 것**은 열려 있습니다.

```csharp
pc.Hand = new List<CardData>();   // ❌ 막힘 — 상자를 바꾸는 것
pc.Hand.Remove(card);             // ✅ 됨   — 상자 안에 손을 넣는 것
pc.Hand.Add(card);                // ✅ 됨
```

> **`private set`은 참조를 보호할 뿐 내용을 보호하지 않습니다.**
> C#에서 `readonly`도 마찬가지입니다. 참조 보호와 내용 보호는 완전히 다른 문제입니다.

그리고 결정적으로 — **`List<T>`는 "내가 변했다"고 알려주지 않습니다.**
`Remove()`는 내부 배열을 조작하고 끝입니다. 이벤트를 쏠 자리가 없습니다.

`FieldManager`와 비교하면 차이가 선명합니다.

```csharp
// FieldManager — 배열이 private, 변경은 메서드로만
public void PlaceUnit(...) { _field[...] = card; OnUnitPlaced?.Invoke(...); }  // ← 종을 달 자리

// PlayerController — 리스트가 public
pc.Hand.Remove(card);                                                          // ← 종을 달 자리가 없음
```

**`FieldManager`는 문이 하나라 그 문에 종을 달 수 있었고, `PlayerController`는 벽이 뚫려 있어 달 곳이 없었습니다.**

### 인과를 정리하면

```
① 손패를 public List로 노출  (캡슐화를 안 함)
        ↓
② 코드 어디서든 직접 변경 가능 → 변경 지점이 흩어짐
        ↓
③ 이벤트를 발행할 단일 지점이 사라짐
        ↓
④ 변경한 쪽이 UI를 직접 호출 (RefreshHand 87회)
        ↓
⑤ 이제 고치려면 그 87곳을 다 손봐야 함   ← "큰 작업"은 원인이 아니라 결과
```

그리고 우회로가 하나 더 생겼습니다.

```csharp
public static void NotifyStatusChanged()
{
    if (FindFirstObjectByType<HUDView>() is HUDView hud)   // 호출할 때마다 씬 전체 탐색
        hud.RefreshStatus();
}
```

"이벤트를 쓰고 싶은데 발행자가 없으니 아무 데서나 부를 수 있게 만들자"의 결과물입니다.
편하지만 결국 **로직이 UI를 아는 상태**로 돌아왔습니다.

## 6. 이건 "처음부터 잘못"이었나

교과서 기준으로는 설계 결함이 맞습니다. 다만 **같은 프로젝트, 같은 시기에 `FieldManager`는 제대로 했습니다.**
원칙을 몰라서가 아니라는 뜻입니다. 그럼 왜 갈렸을까요?

**필드는 처음부터 규칙이 있는 대상이었습니다.** 3칸뿐이고, 아무 데나 못 놓고, 놓으면 엔트리 효과가 터져야 합니다.
**애초에 메서드가 필요했습니다.**

**손패는 처음엔 그냥 카드 목록이었습니다.** 뽑으면 넣고 내면 뺍니다.
그때는 `List<CardData>`가 정확히 맞는 선택이었고, 그 시점에 `AddToHand()` + `OnHandChanged`를 만들었다면 과설계였을 겁니다.

```
초기:  손패를 만지는 곳 몇 곳 · UI 1개           →  List로 충분
지금:  효과 핸들러 440개가 손패를 만짐 · UI 여럿  →  감당 안 됨
```

> **결정이 틀렸다기보다 결정의 유효기간이 끝난 것입니다.** 그리고 그 순간은 조용해서 아무도 알아채지 못합니다.

덧붙이면, 이 프로젝트에서 "잘 된 구조"라 부르는 것들은 **전부 나중에 정리한 것**입니다.
행동 관문도, 선택 중개소도, 효과 핸들러 레지스트리도 처음부터 있던 게 아니라 아파진 뒤에 만들었습니다.
손패는 아직 그 차례가 오지 않았을 뿐입니다.

## 7. 고친다면 — 컴파일러에게 일을 시킨다

```csharp
private readonly List<CardData> _hand = new();
public IReadOnlyList<CardData> Hand => _hand;    // 읽기만 가능 (Add/Remove 없음)

public event Action OnHandChanged;

public void AddToHand(CardData c)      { _hand.Add(c);    OnHandChanged?.Invoke(); }
public bool RemoveFromHand(CardData c) { bool r = _hand.Remove(c); if (r) OnHandChanged?.Invoke(); return r; }
```

`IReadOnlyList`로 내보내면 밖에서는 읽기만 되고, 변경은 반드시 메서드를 지납니다.
그 메서드가 곧 종을 달 자리입니다.

그리고 중요한 건 — **바꾸는 순간 `pc.Hand.Remove(...)`를 쓰던 곳이 전부 컴파일 에러가 납니다.**
100곳이 넘어도 하나씩 고치면 되고, **빠뜨릴 수가 없습니다.**
(문자열 키가 조용히 실패하던 핸들러 레지스트리와 정반대입니다 — 여기서는 타입 시스템이 내 편입니다.)

덤으로 **"UI 갱신을 빼먹어서 화면이 안 바뀌는" 버그가 구조적으로 사라집니다.**
지금은 새 효과를 만들 때마다 `RefreshHand()`를 기억해서 써야 하고, 빼먹으면 카드를 뽑았는데 손패에 안 보입니다.

## 8. 그래서 언제 이벤트를 쓰는가

이 프로젝트에서 두 방식이 갈린 지점에는 규칙성이 있습니다.

| | 이벤트(방송) | 직접 호출(푸시) |
|---|---|---|
| **쓰인 곳** | 필드 유닛, 턴/페이즈, 공격 상태 | 손패, 코스트, 대미지존 |
| **듣는 쪽 수** | 여럿 (`OnPhaseChanged` 구독자 7개) | 하나 |
| **발행 지점** | 소수 (`FieldManager` 안 6곳) | 다수 (효과 코드 전역) |

`OnPhaseChanged`를 보면 이벤트가 왜 이기는지 명확합니다.
`HUDView` · `PhaseBarView` · `HandView` · `AIHandView` · `DamageZoneView` · `SkillZoneSlot` · `AISkillZoneView` —
일곱 군데가 듣습니다. 직접 호출이었다면 `ChangePhase()` 안에 일곱 줄이 있었을 겁니다.

반대로 `RefreshHand()`는 듣는 쪽이 하나뿐이라 이벤트로 만들어도 얻는 게 적습니다.

> **판단 기준은 "듣는 쪽이 몇이고, 앞으로 늘어날 것인가."**
> 1:다면 이벤트. 1:1이고 늘어날 일이 없으면 직접 호출도 합리적입니다.
> 이벤트도 공짜가 아닙니다 — 구독/해제 관리, 호출 흐름이 코드에서 안 보임(디버깅 난이도), 순서 보장 없음이라는 비용이 있습니다.

그리고 실용적인 안전망도 하나 배웠습니다. `DamageZoneView`는 이렇게 해둡니다.

```csharp
TurnManager.Instance.OnPhaseChanged += _ => Refresh();   // 페이즈가 바뀌면 어차피 다시 그린다
```

`NotifyDamageChanged()`를 어디서 빼먹어도 **다음 페이즈에는 화면이 맞아집니다.**
정밀하게 추적하는 대신 **주기적으로 통째로 맞추는** 접근이고, 상태 복제에서 "매번 전체 스냅샷을 보낸다"고 한 것과 같은 발상입니다.

## 9. 정리

- 이벤트는 **"일이 생겼다"고 방송만 하고 누가 듣는지 모르는 것**. 그래서 로직이 UI를 몰라도 된다.
- 방송은 전체에 가므로 **걸러 듣는 건 듣는 쪽 책임**.
- **`+=` 를 썼으면 반드시 `-=`.** 안 하면 파괴된 오브젝트가 호출되고 메모리가 샌다. 종료 순서를 못 믿으니 `null` 체크도 필요하다.
- 이 프로젝트는 **이벤트 8곳 vs 직접 호출 150곳 이상**. 원칙이 지켜진 곳과 아닌 곳이 공존한다.
- 원인은 **`public List` 노출**. 참조만 보호하고 내용은 열어둔 탓에 변경 지점이 흩어졌고, 이벤트를 발행할 자리가 사라졌다.
- 고치는 방법은 **`IReadOnlyList` + 메서드 + 이벤트**. 바꾸는 순간 컴파일러가 호출부를 전부 찾아준다.
- 이벤트를 쓸지는 **듣는 쪽의 수**로 판단한다. 이벤트도 비용이 있다.

> **변경 지점을 좁히면 거기에 무언가를 걸 수 있다.**
> 이벤트 발행, 로그, 검증, 네트워크 동기화 — 전부 "여기를 반드시 지나간다"는 자리가 있어야 걸 수 있다.
> 행동 관문도, 복제 전용 통로도, `FieldManager.PlaceUnit`도 결국 같은 이야기였다.
