# 턴제 게임의 심장은 `while(true)` 한 줄이었다 — 코루틴으로 흐름 되찾기

> Unity TCG(니벨아레나) 개발기 2편.
> [1편](01-단일관문-GameActionGateway.md)에서 "스킬 효과 해결은 비동기라 관문 밖에 남았다"고 적었는데,
> 그 **비동기**의 정체가 이번 글의 주제입니다.

---

## 1. 게임은 "기다림"으로 가득한데, 함수는 기다릴 줄 모른다

턴 하나를 진행한다고 해봅시다.

```
레벨업 → (0.5초 연출) → 드로우 → (0.3초) → 메인페이즈 → (플레이어가 끝낼 때까지 무한정)
      → 어택페이즈 → (방어 팝업이 뜨면 사람이 누를 때까지) → 엔드페이즈 → 턴 교대 → 반복
```

"기다린다"가 다섯 번 나오는데, 성격이 전부 다릅니다. 시간을 기다리기도 하고, 사람의 클릭을 기다리기도 하죠.

문제는 **Unity의 `Update()`는 매 프레임 처음부터 끝까지 실행되고 끝난다**는 것입니다. 중간에 멈출 방법이 없어요.
그래서 코루틴 없이 구현하면 이렇게 됩니다.

```csharp
// 😱 상태 머신 지옥
enum State { LevelUp, LevelUpWait, Draw, DrawWait, Main, Attack, AttackWaitDefense, ... }
State _state; float _timer;

void Update() {
    switch (_state) {
        case State.LevelUp:     레벨업(); _timer = 0.5f; _state = State.LevelUpWait; break;
        case State.LevelUpWait: _timer -= Time.deltaTime; if (_timer <= 0) _state = State.Draw; break;
        case State.Draw:        ...
    }
}
```

동작은 합니다. 그런데 **흐름이 코드에서 사라집니다.**
"레벨업 다음에 드로우"라는 순서가 `_state` 대입문에 흩어져서, 코드를 읽어도 게임 규칙이 보이지 않아요.
페이즈를 하나 끼워넣으려면 상태를 두 개 추가하고 대입문 여러 개를 고쳐야 하고요.

## 2. 코루틴 = 중간에 멈췄다가 **그 자리에서** 다시 시작하는 함수

정의는 이 한 줄이면 충분합니다.

> `yield return`을 만나면 함수가 **거기서 멈추고**, 조건이 풀리면 **바로 그 다음 줄부터** 이어서 실행된다.

📖 책갈피를 끼우고 책을 덮었다가, 나중에 그 페이지를 펴서 계속 읽는 것.
중요한 건 **지역 변수가 그대로 살아있다**는 점입니다. 상태를 필드로 빼서 보관할 필요가 없어요.

가장 작은 실제 예가 토스트 페이드입니다.

```csharp
private IEnumerator Fade(float from, float to)
{
    float t = 0f;
    while (t < FadeDuration)
    {
        t += Time.deltaTime;
        _group.alpha = Mathf.Lerp(from, to, t / FadeDuration);
        yield return null;          // ← "이번 프레임은 여기까지. 다음 프레임에 이 줄 다음부터"
    }
    _group.alpha = to;
}
```

`while` 루프인데 게임이 멈추지 않습니다. **한 바퀴가 곧 한 프레임**이니까요.

여기서 가장 흔한 오해 하나를 짚고 갑니다.

> ⚠️ **코루틴은 멀티스레드가 아닙니다.** 전부 메인 스레드에서 돕니다.
> "동시에 실행"이 아니라 "잘게 쪼개서 번갈아 실행"이에요.
> 그래서 코루틴 안에서 `transform`이든 UI든 마음대로 만져도 안전합니다. (진짜 스레드였다면 Unity API 호출 자체가 금지)

## 3. 이 게임의 뼈대 자체가 코루틴이다

`TurnManager.RunTurn()` — 게임 전체가 **함수 하나**입니다.

```csharp
private IEnumerator RunTurn()
{
    while (true)
    {
        OnTurnChanged?.Invoke(IsPlayerTurn);

        yield return StartCoroutine(LevelUpPhase());
        yield return StartCoroutine(DrawPhase());
        yield return StartCoroutine(MainPhase());
        yield return StartCoroutine(AttackPhase());
        yield return StartCoroutine(EndPhase());

        IsPlayerTurn = !IsPlayerTurn;      // 턴 교대
        if (IsPlayerTurn) TurnNumber++;
    }
}
```

`while(true)` 무한 루프인데 게임이 프리징되지 않습니다. 각 페이즈가 `yield`로 양보하니까요.

그리고 **읽으면 게임 규칙이 그대로 보입니다.** 레벨업 → 드로우 → 메인 → 어택 → 엔드 → 교대.
상태 머신으로 짰다면 이렇게 읽히지 않았을 겁니다. 이게 코루틴의 진짜 값어치예요 — 성능이 아니라 **가독성**.

`yield return StartCoroutine(X)` = **"X가 완전히 끝날 때까지 기다린 뒤 다음 줄로."**
코루틴이 코루틴을 기다리는 중첩이고, 이 한 줄이 페이즈 순서를 보장합니다.

## 4. ★ 사람의 클릭을 어떻게 기다리는가 — 콜백과 코루틴을 잇는 다리

이번 글에서 가장 중요한 부분이고, **1편의 `ChoiceBroker`와 이어지는 지점**입니다.

1편에서 봤듯 선택의 단일 지점인 `ChoiceBroker.DecideDefense`는 **콜백 방식**입니다.

```csharp
if (IsLocalHuman(defenderIsPlayer)) DefensePopup.Instance.Show(..., onDecided, ...); // 팝업 → 언젠가 콜백
else if (NetHub.IsOnline)           NetHub.RequestDefense(..., onDecided, ...);      // 네트워크 → 언젠가 콜백
else                                onDecided(autoDecide());                          // AI → 즉시 콜백
```

문제는 성격이 안 맞는다는 것입니다.
**팝업은 "언젠가" 콜백을 부르는데, 전투 코드는 "지금" 답을 알아야 다음 줄로 갈 수 있습니다.**

이 둘을 잇는 다리가 **플래그 + `WaitUntil`** 3단 관용구입니다. (`CombatManager.PlayerAttackLane`)

```csharp
bool decided = false, result = false;

ChoiceBroker.DecideDefense(false, attacker, defender,
    autoDecide: () => AIDecideDefense(attacker, defender),
    onDecided:  c => { result = c; decided = true; },   // ① 답이 오면 플래그를 세운다
    attackerPower: pw.atk, defenderPower: pw.def);

yield return new WaitUntil(() => decided);              // ② 그 플래그가 설 때까지 여기서 멈춘다

aiBlocks = result;                                      // ③ 답을 손에 쥔 채로 재개
```

세 줄이지만 하는 일이 큽니다.

| 방어자가 | 실제로 벌어지는 일 |
|---|---|
| **사람** | 팝업이 뜨고, 누를 때까지 **몇 초든** 이 줄에서 대기 |
| **AI** | 콜백이 즉시 호출돼 `decided=true` → **같은 프레임에** 통과 |
| **원격 클라** | 네트워크 왕복 동안 대기하다 응답이 오면 통과 |

그리고 **`PlayerAttackLane`은 이 셋 중 무엇이었는지 전혀 모릅니다.** `bool` 하나를 받았을 뿐이에요.

> 1편의 문장이 여기서 완성됩니다.
> **브로커가 "누가 답하나"를 감추고, 코루틴이 "얼마나 걸리나"를 감춥니다.**
> 둘이 한 쌍이라, 전투 코드는 오프라인인지 온라인인지 사람인지 AI인지 모른 채로 그대로 돌아갑니다.

## 5. yield 사전 — 실제로 쓰는 다섯 가지

| 문법 | 의미 | 이 프로젝트의 용례 |
|---|---|---|
| `yield return null` | 한 프레임 양보 | 토스트 페이드 |
| `yield return new WaitForSeconds(0.5f)` | 시간 대기 | 페이즈 연출 딜레이, AI 행동 간격 |
| `yield return new WaitUntil(() => 조건)` | 조건이 **참이 될 때까지** | 방어 선택 대기, 메인페이즈 종료 대기 |
| `yield return new WaitWhile(() => 조건)` | 조건이 **거짓이 될 때까지** | 트리거 타겟 선택 중 대기 |
| `yield return StartCoroutine(X)` | X가 끝날 때까지 | 페이즈 순차 실행, 멀리건 |

`WaitUntil`이 쓰인 다른 자리를 보면 감이 확 옵니다.

```csharp
// TurnManager.MainPhase — 플레이어 입력 대기. UI에서 EndMainPhase() 호출하면 풀린다
yield return new WaitUntil(() => _mainPhaseEnded);
```

**메인 페이즈 전체가 "플레이어가 페이즈바를 누를 때까지 멈춰 있는 한 줄"** 입니다. 몇 초든 몇 분이든.

`WaitWhile`은 방향이 반대입니다.

```csharp
// 트리거로 프라이즈 선택 UI가 떴으면 플레이어가 고를 때까지 대기
yield return new WaitWhile(() => SkillZoneSlot.IsTriggerTargeting);
```

"선택 중인 **동안** 대기"라서 `WaitWhile`.
전투 도중 트리거가 터져 선택 UI가 뜨면, 그게 정리될 때까지 뒷처리를 미룹니다.

## 6. ★ 왜 "공격만" 특별 취급인가 — 동기 관문과 비동기 전투의 경계

프로젝트 메모에 이런 줄이 있습니다. *"공격은 코루틴이라 완료 후 BroadcastState 추가"*.
1편과 2편을 겹쳐야 이게 왜 필요한지 보입니다.

1편의 `Gateway.Submit`은 **동기 함수**였습니다. 검증하고, 실행하고, `bool`을 돌려주고 끝.
그런데 공격만 사정이 다릅니다.

```csharp
private static bool ExecuteDeclareAttack(GameAction a)
{
    if (!IsTurnPhase(a.IsPlayer, PhaseType.Attack)) return false;
    if (!CombatManager.Instance.CanAttack(a.Lane))  return false;

    CombatManager.Instance.StartCoroutine(CombatManager.Instance.PlayerAttackLane(a.Lane));
    return true;   // ← 전투는 시작만 됐는데 벌써 true를 반환한다
}
```

`StartCoroutine`은 **시작만 시켜놓고 즉시 돌아옵니다.** 방어 팝업이 뜨든 말든 `Submit`은 그 자리에서 `true`를 뱉어요.

그래서 문제가 생깁니다. 1편에서 본 `Submit` 안쪽의 온라인 복제가—

```csharp
bool ok = Execute(action);
if (ok && NetHub.IsOnline) NetHub.BroadcastState();   // ← 전투 시작 "직후"의 상태를 복제
```

**아직 끝나지도 않은 전투의 상태를 복제**하게 됩니다. 상대 화면에는 공격 결과가 반영되지 않죠.

해결은 코루틴 **끝**에서 한 번 더 복제하는 것이었습니다.

```csharp
    MarkAttacked(true, lane);

    // 플레이어 공격(코루틴) 완료 후 결과 상태 복제
    if (NetHub.IsOnline && NetHub.IsAuthority) NetHub.BroadcastState();
}
```

교훈은 하나로 요약됩니다.

> **`StartCoroutine`은 `await`가 아닙니다. "시작"이지 "완료"가 아니에요.**
> 동기 함수(`bool` 반환)와 코루틴이 만나는 경계에서는, 완료 시점의 처리를 코루틴 쪽 끝에 따로 붙여야 합니다.

1편 9장에서 "스킬 효과 해결은 아직 관문 밖에 남아 있다"고 적었던 것도 정확히 같은 이유입니다.
`bool` 반환값 하나로는 **아직 오지 않은 결과**를 표현할 수 없으니까요.

## 7. 겪어봐야 아는 함정 셋

### ① 코루틴은 `MonoBehaviour`에 얹혀 산다

`GameActionGateway`는 `static class`라 코루틴을 돌릴 수 없습니다. 그래서 남의 것을 빌립니다.

```csharp
CombatManager.Instance.StartCoroutine(CombatManager.Instance.PlayerAttackLane(a.Lane));
//        ↑ 이 오브젝트가 코루틴의 "주인"
```

그리고 **주인이 비활성화(`SetActive(false)`)되거나 파괴되면 코루틴은 그 자리에서 조용히 죽습니다.**
예외도 로그도 없이, 중간에서 멈춘 채로요.
그래서 팝업 같은 UI 오브젝트에 긴 코루틴을 붙이는 건 위험하고, 매니저에 붙여둔 건 안전한 선택입니다.

### ② 온라인 클라이언트는 이 심장을 아예 돌리지 않는다

```csharp
// TurnManager
if (NetHub.IsOnline && !NetHub.IsAuthority)
{
    Debug.Log("[Turn] 온라인 클라 — 턴 루프 미실행(호스트 권위, 상태 수신만)");
    return;    // ← StartCoroutine(RunTurn()) 자체를 안 한다
}
```

클라는 `RunTurn`을 시작조차 하지 않습니다. 각자 턴 루프를 돌리면 두 화면이 어긋나니까요.
대신 `ApplyNetworkTurn()`으로 **호스트가 알려준 턴/페이즈를 화면에만 반영**합니다.

> **온라인에서 게임의 시간은 호스트에게만 흐릅니다.** 클라는 그 결과를 비추는 화면입니다.
> 1편의 "호스트 권위"가 코루틴 층위에서는 이런 모습으로 나타납니다.

### ③ `WaitUntil`의 조건식은 매 프레임 평가된다

`WaitUntil(() => decided)`는 프레임마다 그 람다를 호출합니다.
조건 안에서 무거운 계산(리스트 전체 순회 같은 것)을 하면 대기하는 내내 비용이 듭니다.
이 프로젝트처럼 **`bool` 플래그 하나만 보게** 하는 게 정석이에요.

## 8. 정리

- 코루틴은 **`yield`에서 멈췄다가 그 자리에서 재개하는 함수**다. 덕분에 "기다림"을 상태 머신이 아니라 **읽히는 순서 그대로** 쓸 수 있다.
- 이 게임의 심장은 `RunTurn()` — **`while(true)` + 페이즈 코루틴 5개**. 코드를 읽으면 곧 게임 규칙이 보인다.
- 사람의 입력은 **콜백 → 플래그 → `WaitUntil`** 3단 관용구로 코루틴 흐름에 합류시킨다. 그래서 전투 코드는 답한 주체가 사람인지 AI인지 원격인지 모른다.
- 단 **`StartCoroutine`은 시작일 뿐 완료가 아니다.** 동기 관문과 만나는 경계(= 공격)에서는 완료 처리를 코루틴 끝에 따로 붙여야 한다.

1편이 **"누가 실행하는가"**(권한의 경계)에 관한 이야기였다면,
2편은 **"언제 실행되는가"**(시간의 경계)에 관한 이야기였습니다.

> **브로커가 "누가 답하나"를 감추고, 코루틴이 "얼마나 걸리나"를 감춘다.**
> 그 둘 덕분에 전투 코드는 아무것도 모른 채 그대로 있을 수 있었다.
