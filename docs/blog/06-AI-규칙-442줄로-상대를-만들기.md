# 탐색 알고리즘 없이 만든 카드게임 AI — 규칙 442줄로 어디까지 되나

> Unity TCG(니벨아레나) 개발기 6편.
> 미니맥스도 몬테카를로도 없습니다. 사람이 손으로 적은 규칙만 442줄.
> **그게 왜 합리적이었는지, 그리고 어디서 무너지는지**에 대한 글입니다.

---

## 1. AI가 내리는 결정은 네 가지뿐

```
① 어떤 카드를 어느 레인에 배치할까
② 업그레이드할까, 한다면 어느 레인을
③ 아이템을 누구에게 장착할까
④ 공격할까 / 방어할까
```

그리고 중요한 성질이 하나 있습니다. **이 결정들은 서로를 모릅니다.**
①을 할 때 ④를 고려하지 않습니다. 각각 독립된 규칙 뭉치입니다.

---

## 2. 배치 — 정렬하고 위에서부터 채운다

```csharp
List<CardData> playable = ai.Hand
    .Where(c => c.Type == CardType.Unit && (낼 수 있는 카드))
    .OrderByDescending(c => c.AttackPower)      // ★ 파워 높은 순
    .ToList();

foreach (CardData card in playable)
{
    if (빈 레인 있음)              { 배치; continue; }
    if (업그레이드 가능한 레인 있음) { 업그레이드; }
}
```

전략이 한 줄로 요약됩니다. **"낼 수 있는 것 중 제일 센 걸 낸다."**

레인 선택은 더 단순합니다.

```csharp
int lane = deployableLanes[Random.Range(0, deployableLanes.Count)];   // 랜덤
```

**빈 레인 중 아무 데나** 놓습니다. "상대의 약한 유닛 앞에 놓자" 같은 판단이 없습니다.

업그레이드 대상만 조금 영리합니다.

```csharp
// 업그레이드 가능한 레인 중 파워가 가장 낮은 레인 반환 (교체 효율 최대화)
if (pow < bestPow) { bestPow = pow; best = i; }
```

**제일 약한 유닛을 교체합니다.** 강한 걸 갈아치우면 손해니까요.
규칙 한 줄로 실제 이득을 내는 좋은 예입니다.

---

## 3. 아이템 — 우선순위 목록

이 AI에서 가장 잘 만들어진 부분입니다.

```csharp
private int DecideItemTargetLane(CardData item)
{
    // 1순위: 조우 중이고 AI가 지고 있는 레인 (아이템으로 역전 가능성)
    for (int i = 0; i < 3; i++)
        if (aiPow < plPow) return i;

    // 2순위: 다이렉트 어택 가능한 레인 (아이템 어태커 효과 활용)
    for (int i = 0; i < 3; i++)
        if (앞이 비어있음) return i;

    // 3순위: 가장 강한 아군 유닛 레인
    ...
}
```

**"먼저 A를 시도하고, 안 되면 B, 그것도 안 되면 C."**
휴리스틱 AI의 전형적인 형태이고, 장점이 분명합니다.

- **읽으면 의도가 보인다** — 주석 없이도 "역전 > 다이렉트 강화 > 무난하게"가 읽힘
- **고치기 쉽다** — 순서만 바꾸면 성격이 바뀜
- **디버깅이 된다** — 왜 저기 장착했는지 코드를 따라가면 나옴

신경망이나 탐색 기반이면 "왜 저렇게 뒀지?"를 설명할 수 없습니다.
**작은 게임에서는 이게 압도적으로 실용적입니다.**

---

## 4. 공격 — 이기면 하고, 지면 아이템을 먼저 시도한다

```csharp
int aiPower = GetEffectivePower(false, lane, attacker);
int plPower = GetEffectivePower(true,  lane, defender);

if (aiPower < plPower)
{
    bool berserker = EffectSystem.Instance.IsBerserker(false, lane, attacker);
    if (!berserker)
    {
        boosted = TryEquipItemForLane(lane, plPower - aiPower);   // 부족한 만큼 메울 아이템 찾기
        aiPower = GetEffectivePower(false, lane, attacker);        // 장착 후 재계산
    }
    if (aiPower < plPower && !berserker)
    {
        ToastView.Show($"레인{lane + 1} 공격 포기");
        continue;
    }
}
```

기본은 "이길 때만 공격"인데 두 가지가 얹혀 있습니다.

**① 아이템으로 역전 시도** — 부족한 양(`plPower - aiPower`)을 인자로 넘겨 "이만큼 메울 아이템 있어?"를 묻고,
장착했으면 **다시 계산**합니다. 규칙 기반인데도 제법 사람 같은 절차입니다.

**② 광전사 예외** — "이길 수 없어도 조우 유닛이 있으면 반드시 공격"이라는 카드 키워드가 AI 판단보다 우선합니다.
**게임 규칙이 AI 전략을 덮어쓰는** 구조입니다.

## 5. ★ 방어 — 여기서 무너진다

```csharp
private bool AIDecideDefense(CardData attacker, CardData defender)
{
    int atkPower = attacker.AttackPower + ParseAttackerBonus(attacker);
    int defPower = defender.AttackPower;
    return defPower > atkPower;   // 동점이면 방어 유닛이 트래시되므로 방어 안 함
}
```

세 줄인데 두 군데가 잘못돼 있습니다.

### ① 인쇄 파워로 판단한다

`attacker.AttackPower` — 버프도, 디버프도, 아이템도, 패시브 아우라도, 리더 패시브도 **전부 무시**합니다.

바로 위의 공격 판단은 `GetEffectivePower`(모든 층을 합산한 실제 수치)를 제대로 쓰는데, **방어만 인쇄값**입니다.

```
공격자: 인쇄 3000 + 버프 2000 = 실제 5000
방어자: 4000
AI 판단: "4000 > 3000이니 이긴다!" → 방어 → 죽음
```

### ② 효과 텍스트를 파싱한다

```csharp
private int ParseAttackerBonus(CardData card)
{
    if (!card.Keywords.Contains("어태커")) return 0;
    string text = string.Join(" ", card.Effects);     // 사람이 읽는 한국어
    int idx = text.IndexOf("파워+");                   // "파워+"를 찾아서
    for (int i = idx + 3; char.IsDigit(text[i]); i++) // 뒤의 숫자를 긁는다
        numStr += text[i];
}
```

이 프로젝트의 제1원칙이 **"효과는 `effectTypes`로 관리한다, 텍스트 파싱 금지"** 인데,
`"AttackerPowerBoost:2000"`이라는 정형 데이터를 두고 한국어 문장에서 `"파워+"`를 찾고 있습니다.

"파워+"가 여러 번 나오면 첫 번째만 잡고, "파워-"는 못 잡고, 문구가 조금만 달라도 못 잡습니다.

### 더 아쉬운 건 — 정답이 바로 옆에 있다

```csharp
var pw = PreviewPowers(true, lane, attacker, lane, defender);   // ← 정확한 수치를 이미 계산

ChoiceBroker.DecideDefense(false, attacker, defender,
    autoDecide: () => AIDecideDefense(attacker, defender),      // ← 안 쓰고 다시(틀리게) 계산
    attackerPower: pw.atk, defenderPower: pw.def);              // ← 사람 팝업엔 정확한 값 전달
```

**사람에게는 정확한 수치를 보여주고, AI는 틀린 수치로 판단합니다.**

이건 전에 한 번 고친 버그와 같은 계열입니다.
방어 팝업이 인쇄 파워를 표시해서 플레이어가 이길 방어를 패스하던 문제 — 원인은 "계산식이 두 벌"이었고,
그때 팝업은 고쳤지만 **AI 쪽 계산은 그대로 남아 있었습니다.**

> **같은 개념에 계산 경로가 둘이면 반드시 어긋납니다.** 한쪽만 고치면 나머지가 남습니다.

수정 자체는 간단합니다. `autoDecide`가 이미 계산된 `pw.atk / pw.def`를 쓰도록 바꾸고 `ParseAttackerBonus`를 지우면 됩니다.

## 6. AI가 약한 근본 이유 셋

### ① 1수도 보지 않는다

"이 유닛으로 공격하면 → 상대가 어떻게 반격하나"를 **전혀 계산하지 않습니다.**
지금 이 순간의 파워 비교만 합니다. 체스로 치면 "지금 잡을 수 있는 말이 있으면 잡는다" 수준입니다.

### ② 행동 순서를 정할 수 없다

코드에 적힌 순서로만 움직입니다. 액티브 → 공격, 레인 0 → 1 → 2.
그 한계가 주석에 솔직하게 적혀 있습니다.

```csharp
// ※ AI 한계: 이 판단은 실제 공격 이전에 실행되므로, "먼저 공격해 엑시트를 부여받은 뒤
//   트래시" 콤보는 AI가 활용하지 못함(정적 엑시트만 인식).
//   플레이어는 클릭 순서를 자유롭게 정할 수 있어 가능.
```

**"순서를 자유롭게 정할 수 있다"** 는 사람의 큰 강점인데, 이 AI는 순서 자체가 코드에 박혀 있어 흉내낼 수 없습니다.

## 7. 그런데 왜 이걸로 충분했나

**이번 글에서 가장 중요한 판단입니다.**

이 게임의 목표는 "친구용 MVP"였습니다. AI는 온라인 상대가 없을 때 연습하는 용도이고,
"이길 수 있는 상대" 정도면 충분합니다.

그리고 게임 구조 자체가 규칙 기반 AI에 유리합니다.

- 레인이 **3개**뿐 — 배치 조합의 폭이 작다
- 조우가 **1:1 파워 비교** — 규칙으로 표현하기 쉽다
- 카드 효과가 대부분 **즉발** — 장기 계획의 비중이 낮다

**여기에 탐색 AI를 붙였다면 그게 과설계였을 겁니다.**
아프지 않은 곳을 미리 고치는 일은 대개 낭비로 끝납니다.

그리고 한 가지 안전장치가 여기서 값을 합니다.

```csharp
// AIController — 사람과 똑같은 관문을 지난다
GameActionGateway.Submit(new GameAction { Type = PlaceUnit, IsPlayer = false, ... })
```

AI가 아무리 단순해도 **코스트를 무시하거나 규칙을 어길 수는 없습니다.** 검증이 관문 안에 있기 때문입니다.
"AI만 치트한다"는 흔한 버그가 구조적으로 불가능합니다.

> 단순한 AI일수록 이 안전장치가 값을 합니다.
> AI 코드가 규칙 검증까지 각자 하고 있었다면, 검증이 두 벌이 되어 사람과 AI가 다른 게임을 하게 됐을 겁니다.

## 8. 더 똑똑하게 만들려면

### 탐색(MCTS/미니맥스)은 TCG에서 어렵다

- **히든 정보** — 상대 손패와 덱을 모릅니다. 체스처럼 판이 다 보이지 않아, 제대로 하려면 "가능한 상대 손패"를 확률적으로 다루는 결정화(determinization)가 필요합니다
- **분기 폭발** — 손패 7장 × 레인 3개 × 아이템 × 스킬… 한 턴의 선택지만 수백 가지
- **시뮬레이션 비용** — 효과가 700종이라 가상으로 돌려보는 것 자체가 무겁습니다

### 현실적인 개선은 두 단계

**1단계 — 평가 함수 도입.** "이 판이 나에게 얼마나 좋은가"를 하나의 점수로 만듭니다.

```
점수 = 아군 파워합 - 적 파워합 + 손패수 × α - 대미지존 × β …
```

그러면 배치 레인을 랜덤이 아니라 **점수가 가장 높아지는 곳**으로 고를 수 있고,
지금 흩어져 있는 우선순위 규칙들을 하나의 기준으로 통일할 수 있습니다. 작업량도 작습니다.

**2단계 — 1수 시뮬레이션.** "이 수를 두면 점수가 어떻게 되나"를 실제로 계산해봅니다.
여기까지만 가도 체감이 크게 달라지는데, **전제 조건이 하나 있습니다.**

> 게임 상태를 **복사해서 가상으로 돌려볼 수 있어야** 합니다.
> 현재 구조는 `FieldManager`/`EffectSystem`이 싱글톤 실물이라 불가능합니다.

재밌는 건 — **온라인 동기화용 상태 스냅샷이 이미 그 절반**이라는 점입니다.
판 전체를 16칸 배열로 직렬화하는 코드가 이미 있으니까요.
그걸 "네트워크로 보내기" 대신 "가상으로 되돌리기"에 쓰면 시뮬레이션의 토대가 됩니다.

**멀티플레이를 위해 만든 것이 AI 개선의 발판이 되는** 셈인데, 이런 게 구조를 잘 잘라둔 덕에 생기는 이득입니다.

## 9. 정리

- AI는 **442줄의 규칙 뭉치**. 탐색 알고리즘 없음. 결정 네 가지는 **서로를 모른다.**
- 배치는 "제일 센 카드를 아무 빈 레인에", 업그레이드는 "제일 약한 걸 교체", 아이템은 **우선순위 목록**.
- 공격은 "이기면 한다" + **부족분만큼 아이템으로 메워보고 재계산**하는 제법 사람 같은 절차.
- **방어 판단만 인쇄 파워 + 텍스트 파싱**으로 어긋나 있다. 정확한 수치가 바로 옆에서 계산되는데도 쓰지 않는다.
- 약한 이유는 **1수도 안 봄 · 순서를 못 정함 · 계산 경로 일부 오류**. 그래도 이 게임 규모에서는 합리적인 선택이었다.
- AI도 **행동 관문을 지나므로 규칙 위반이 구조적으로 불가능**하다. 단순한 AI일수록 이 안전장치가 값을 한다.
- 개선은 **평가 함수 → 1수 시뮬레이션** 순. 후자는 상태 복사가 전제이고, **온라인용 스냅샷이 그 출발점**이 될 수 있다.

> 좋은 AI를 만드는 것과, **지금 필요한 만큼의 AI를 만드는 것**은 다른 문제다.
> 그리고 대부분의 프로젝트에서 필요한 건 후자다.
